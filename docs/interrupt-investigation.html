Range updates: what is known and what still needs checking

The dashboard change is independent of firmware. Weekly bars now count recorded lightning observations only. Range updates are hidden from the distance chart and default history view. They remain available through the chart’s Sensor diagnostics option, history filters and JSON export. Existing records are preserved and are not relabeled as lightning.

What the records show

Field records include distance estimates appearing seconds after routine station uploads, often followed by an out-of-range update roughly 17 minutes later. Some updates have no preceding recorded lightning event. This association makes activity during wake-up or radio operation a useful investigation target. It does not establish whether the initiating signal was real lightning, electrical interference, or a mishandled interrupt.

The AS3935 documentation describes reason code zero as an estimate revision when old events are purged. That explains why legitimate updates can occur without a new strike, but does not prove the cause of every record in this deployment. The weekly chart is therefore an observation count, not a count of independently verified physical strikes.

Findings in the source

FindingMeaning
Fallback classificationThe previous reader treated any reason without recognized lightning/noise/disturber bits as a range update. Reserved or invalid values could receive that label. However, valid distances were read only for zero or lightning codes: this fallback alone does not explain the stored updates with valid distances.
Long service gapsWi-Fi association and NTP waits could each take up to eight seconds without servicing the sensor. TLS/HTTP operations also block. SparkFun’s driver comments describe a limited interrupt-reading window, so delayed reads are a plausible contributor, not a confirmed diagnosis.
Missing historical diagnosticsExisting cloud records do not retain raw interrupt codes, wake causes, service gaps or acquisition phase. Historical classifications cannot reliably be reconstructed or promoted to lightning detections.

Prepared firmware 1.0.4

Prepared and build-tested; hardware acceptance is pending. Updating the website does not install this firmware. No OTA path is implemented.

  • Recognizes only documented interrupt codes: zero (range revision), one (noise), four (disturber), and eight (lightning). Invalid/reserved values increase the existing rejected counter instead of becoming observations.
  • Polls the sensor during Wi-Fi association and NTP waits, with a bounded number of captures per connection attempt. This reduces those blind intervals but does not eliminate blocking during TLS/HTTP.
  • Prints a serial diagnostic for each serviced interrupt: raw reason, raw range, acquisition phase, time since boot, interval since the previous sensor poll, and wake cause. These diagnostics are serial output; they are not a new durable cloud telemetry stream.
  • Preserves the event structure, queue format, sequence reservations, endpoint schema and sensor thresholds. It does not suppress listening during Wi-Fi or infer a strike from a zero reason.

The interrupt classifier has an exhaustive host test over all 256 input bytes. Dashboard regression tests check that range updates cannot increase weekly bars, their scale, or default chart counts.

Next hardware session

  1. Back up the existing application and queued data before testing. Flash the application only when authorized; do not run uploadfs, erase NVS or reset the device identity for an ordinary upgrade. Retain the individual sensor’s measured tuning value.
  2. Capture serial logs from a routine heartbeat and an interrupt wake. Compare phase, raw, poll_gap_ms, boot_ms and wake. A zero reason remains ambiguous if the read was delayed.
  3. Use controlled runs to compare radio enabled/disabled while keeping the other acquisition behavior constant, and test awake versus sleep/wake behavior separately. Compare upload timing with new sensor activity. Do not declare every event near an upload false solely from timing.
  4. If radio coupling is reproduced, inspect physical separation, harness routing, power integrity and final antenna tuning before choosing a hardware remedy. Do not simply mask the sensor while transmitting: that would also lose real observations.
  5. Confirm real interrupt classification and wake capture, queue persistence, bounded retries, sensor/storage health and battery current before accepting the prepared firmware for unattended operation.
